# What are the differences in the resolution strategy (`node`, `node16/nodenext`, `bundler`, or `classic`) in TypeScript?


TypeScript offers several module resolution strategies that determine how the compiler locates files referenced by import statements. Each strategy has different rules and use cases.

## Classic Resolution Strategy

The Classic strategy was TypeScript's original resolution method, now primarily maintained for backward compatibility:

- **For relative imports** (starting with `./` or `../`): Looks for `.ts` and `.d.ts` files at the specified path relative to the importing file
- **For non-relative imports**: Walks up the directory tree from the importing file, attempting to locate the module at each level [2] [5]
- **Example**: For `import { x } from "moduleX"` in `/root/src/folder/Y.ts`, it would check locations in this order:
  - `/root/src/folder/moduleX.ts`
  - `/root/src/folder/moduleX.d.ts`
  - `/root/src/moduleX.ts`
  - `/root/src/moduleX.d.ts`
  - And so on up to the root directory [2]
- **Not recommended**: The Classic strategy is considered outdated and should not be used in modern TypeScript projects [7]

## Node Resolution Strategy

The Node strategy (also called `node10`) mimics Node.js's CommonJS resolution algorithm:

- **For relative imports**: Looks for the exact file, then with extensions (.ts, .tsx, .d.ts), then for index files in directories
- **For non-relative imports**: Searches in node_modules directories up the directory tree
- **Purpose**: Designed for older Node.js versions that only support CommonJS `require()` [7]

## Node16/NodeNext Resolution Strategies

These strategies are designed for modern Node.js environments:

- **Dual resolution algorithms**: Intelligently switches between ESM and CommonJS resolution based on the detected module format of each file [6] [7]
- **Format detection**: Uses file extensions (.mts/.cts) and package.json "type" field to determine module format [1]
- **Extension handling**: Respects Node.js's requirement for explicit file extensions in ESM imports
- **Package.json "exports" support**: Honors the "exports" and "imports" fields for package entry point resolution
- **Future-proof**: NodeNext will always align with the latest Node.js behavior, while Node16/Node18 are fixed to specific versions [8]

## Bundler Resolution Strategy

The Bundler strategy is optimized for use with modern JavaScript bundlers:

- **Similar to Node16/NodeNext**: Supports package.json "exports" and "imports" fields
- **Key difference**: Never requires file extensions on relative path imports [7]
- **Purpose**: Aligns with the behavior of tools like Webpack, Vite, esbuild, and similar bundlers

This strategy is ideal for browser-targeted applications that will be processed by a bundler before deployment.

## Choosing the Right Strategy

- For modern Node.js applications: Use `nodenext` or `node16` for both module and moduleResolution [8]
- For browser applications with bundlers: Use `bundler`
- For legacy applications: Use `node10` (formerly just `node`)
- Avoid `classic` in all new projects

The `moduleResolution` setting should be aligned with your target environment to ensure TypeScript's type checking accurately reflects how your code will behave at runtime.
